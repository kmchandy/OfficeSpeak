# Plant-a-gap experiment (investment_club, run_1 base)

Purpose: turn the single Herb-gap anecdote into a **measured** result — does the
explain-back reliably surface a planted defect (detection rate) without flagging
defects that aren't there (false-positive rate)?

## Base graphs (two, both useful)

1. `runs/run_1/actual_graph.md` — Claude's original. An analytical explain-back of
   it found three latent issues (implicit join at Don, Herb's premature fan-out,
   model-portfolio note); that run is itself a result
   (`runs/run_1/explanation_analytical.md`) showing the explain-back surfaces
   coordination coupling in review mode.
2. `reference_graph.md` — the **corrected** base, used as the clean control so a
   flagged defect in a mutant is the *planted* one, not a pre-existing smell. The
   mutants below are cut from this graph.

Both bases are run. Neither supersedes the other.

## Scope note: wiring vs agent-coding

Plant-a-gap tests **wiring** defects (Stage A). M1-M5 are wiring. **M6 is
reclassified** as an agent-coding / contract-conformance fault (Stage B / E1b): a
missing gate-release is a protocol obligation a correct body emits, not a topology
choice. Score M6 under E1b, not the wiring detection rate. (See the broader
wiring-vs-spec separation discussion, in progress.)

## Method (keeps the explainer honest)

The trustworthy signal in run_1/run_2 came because the explanations were produced
in **fresh chats that did not know what was being tested**. Plant-a-gap must keep
that discipline, so the work is split:

1. (this file + `mutants.md`) Define the base graph, six single-defect mutants,
   and a **pre-registered** prediction for each (catch / miss) with reasoning.
2. (Mani, fresh chats) For each mutant and the clean control, start a fresh chat,
   paste `prompt_explain.md` + the mutant graph, and save the explanation. The
   explainer is NOT told a defect was planted or which edge changed.
3. (scoring) Compare each explanation to the pre-registration using the rubric
   below. Because predictions are registered *before* the runs, a catch or miss
   can't be rationalized after the fact.

Pre-registration matters here specifically because the earlier explain-back runs
were generated by the same model that is scoring; registering catch/miss with
reasons in advance is what makes the measurement defensible.

## The six mutants (one planted defect each)

| Mutant | Edit to run_1 | Planted defect | Predicted |
|---|---|---|---|
| M1 | remove `Herb <-> Rachel` | Herb can't read current holdings -> tax/fees on no cost basis | catch |
| M2 | remove gate Gus + its wiring; `fair_merge -> Warren,Bill,Don,Herb`; drop `Don ..done..> Gus` | no one-at-a-time -> concurrent read-modify-write of the shared record | catch |
| M3 | remove `Bill -> Meg`; `Meg = merge_synch(inports:[warren])` | Bill's argument never reaches Don -> decision ignores the opportunities view | catch |
| M4 | `Don <-> Herb` becomes one-way `Don -> Herb` (reply not used) | Don finalizes without waiting for tax/fees | catch |
| M5 | remove `Warren <-> Rachel` | Warren's argument not logged; his practice portfolio not updated | **miss** |
| M6 | remove `Don ..done..> Gus` | gate never released -> office deadlocks after the first item | **miss** |

Full paste-ready graphs are in `mutants.md`.

## Scoring rubric (per mutant explanation)

- **Catch** — the explanation surfaces the planted defect in a way Pat could act
  on: either in the story ("X doesn't reach Y") or in "Baked-in choices" ("nothing
  connects A to B; tell me if..."). The defect must be *named*, not merely
  implied by omission.
- **Partial** — the explanation states the neutral fact that contains the defect
  (e.g., "several items at once") but does not flag it as a choice Pat might want
  changed.
- **Miss** — the explanation describes the mutant graph as if nothing were wrong,
  or silently "repairs" the defect in prose (describes an edge that isn't there).
- **False positive** (control only) — flags a defect the clean graph does not have.

Metrics: detection rate = catches / 6; false-positive rate from the clean control
and from any invented defects in the six mutant runs.

## Pre-registered reasoning (why each prediction)

- **M1 catch** — instruction 4 ("who keeps the shared information and who reads
  it") forces an ownership audit; Herb needs holdings, has no read edge. Same
  class the explainer already caught in run_2, so a catch is *expected*, and
  therefore weaker as independent evidence — noted.
- **M2 catch** — instruction 4 explicitly asks "does it handle one item at a
  time?" With the gate gone the honest answer is "no, several at once," which
  surfaces the change. Whether it further articulates the record-corruption risk
  is the harder part; a bare "several at once" still counts as catch because Pat,
  who set up a shared portfolio, would react.
- **M3 catch** — structural and flow-obvious: Bill produces an argument that goes
  to Rachel but never to the decider. Listing team members and telling the story
  makes a dead-ended worker visible.
- **M4 catch** — instruction 4 asks about back-and-forth/ask-and-wait loops. The
  spec said Don checks with Herb *before* finalizing; a one-way edge with no wait
  contradicts that and a faithful "does he wait?" check exposes it.
- **M5 miss** — a silent omission with no downstream symptom: Warren's argument
  still reaches Don via Meg, so the item's journey is unchanged. Catching it needs
  a per-agent write audit (Bill logs, Warren doesn't) that the prompt does not
  emphasize. Predicting miss (or at best partial).
- **M6 miss** — a liveness/deadlock defect from a missing control edge. The gate
  is glossed as "starts the next only after the current is finished"; an explainer
  will describe that behavior without verifying a done-signal edge exists. A
  describer is not a verifier. Predicting miss.

## What confirmation would establish

If fresh runs land ~M1-M4 catch, M5-M6 miss, control clean: the explain-back
**maps to a coverage envelope** — it reliably surfaces defects that change an
item's journey or that the checklist explicitly probes (serialization, joins,
ask-and-wait, missing input to a consumer), and misses silent omissions and
liveness bugs. That is an honest, non-inflated claim, and it directly motivates a
complementary **static structural check** (unreachable record write; gate with no
matching done-signal) as the systems-layer partner to the HCI explain-back.

If instead M5/M6 are caught, even better for the loop — update the claim upward.
If M1-M4 are missed, the loop is weaker than the anecdote suggested and the paper
says so.

## Limitations

- Six mutants on one office is a pilot, not a rate. Repeat on tutor/debate graphs
  and both substrates before quoting a number.
- Single-defect mutants only; real Pat errors may be multi-edge or semantic.
- "Catch" is judged by us; E3c (non-expert humans reading the explanations) is the
  claim that actually matters and is not substituted by this experiment.
