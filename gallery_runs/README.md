# gallery_runs — end-to-end runs of gallery apps

Each subdirectory logs one gallery app's journey through the whole
toolchain, in the **pseudocode** pipeline:

```
spec.md  →  pseudocode.txt (Claudette)  →  graph.yaml  →  diagram.html  →  run
```

Claude reads `spec.md` under the meta-prompt (`prompts/meta_prompt_v1.md`)
and returns pseudocode in the NoT pseudo-language. Everything after that
is mechanical: `officespeak.parser` turns the pseudocode into a graph,
which compiles to a runnable DSL network. We do **not** generate
office.md — graph.yaml is canonical.

The experiment this records: *does Claude produce correct pseudocode
from the spec?* — measured per app by whether it parses (in-grammar),
whether the decomposition is right, and whether the graph compiles/runs.

## Layout

```
gallery_runs/
  run_pipeline.py          # the driver (scaffold / build-prompt / stage-log)
  <app>/
    spec.md                # Pat's English description
    prompt.txt             # meta-prompt + spec, ready to paste into Claude
    pseudocode.txt         # Claude's pseudocode (paste here)
    warnings.txt           # parser warnings  ]
    graph.yaml             # the parsed graph   ]  generated by
    diagram.html           # open in a browser  ]  run_pipeline.py
    diagram.mermaid        # Git-friendly source ]
    app/graph.yaml         # copy compiled against the DSL role library
    compile.txt            # compile result
    run.log                # execution output (with --execute)
    notes.md               # observations
```

## Workflow

```
python gallery_runs/run_pipeline.py --new <app>        # scaffold (spec + placeholders)
# write spec.md
python gallery_runs/run_pipeline.py --prompt <app>     # build prompt.txt (meta-prompt + spec)
# paste prompt.txt into a fresh Claude chat; paste the reply into pseudocode.txt
python gallery_runs/run_pipeline.py <app>              # log parse -> graph -> diagram -> compile
python gallery_runs/run_pipeline.py <app> --execute    # also run the network
```

## The test set (one app per distinct shape)

Most of the ~20 gallery apps repeat three shapes, so we test one
representative of each rather than all of them:

| App | Shape it exercises |
|---|---|
| `situation_room` | pipeline + binary alert routing (anchor) |
| `inbox_triage` | multi-way router (`if / elif / else`) |
| `debate` | feedback loop + termination |
| `new_grad_jobs` | conditional agent application (grammar stress) |
| `periodic_brief` | agent-free multi-source merge → sink |

`loudness_monitor` (a plain pipeline) is already validated and serves,
with `situation_room`, as a confidence anchor. Everything else in the
gallery is one of these shapes repeated. Automated structural scoring
against hand-written ground truth lives separately in
`examples/sanity_checks/` (driven by `officespeak/harness.py`).

The driver needs `officespeak` on the path (automatic from the repo
root) and, for the compile/run stages, `dissyslab` importable. Parse
and diagram work without dissyslab, so a failed compile is logged
rather than aborting the run.
